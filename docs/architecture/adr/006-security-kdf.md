# ADR 006: Cryptographic Protection and Key Derivation Protocol (Security KDF)

**Date:** 2026-05-05
**Status:** Approved
**Context:** Specification of the crypto provider, the encryption algorithm (AEAD), and password-based key generation (KDF).

## 1. No Proprietary Cryptography
To avoid vulnerabilities (the *Don't roll your own crypto* rule), the project uses only standardized primitives. The `cryptography` library (`hazmat` modules) is the approved crypto provider.

## 2. Approved Standards
*   **Symmetric encryption:** `AES` in `GCM` mode (Galois/Counter Mode). Key length: **256 bits** (32 bytes).
*   **Key Derivation Function (KDF):** `PBKDF2HMAC` with the `SHA-256` hash. Iteration count: **480 thousand** (the NIST recommendation for the current year).
*   **Salt:** **16 bytes**, generated by the cryptographically secure generator `os.urandom(16)` for each new embedding session.
*   **Initialization vector (Nonce/IV):** **12 bytes**, generated via `os.urandom(12)`.

## 3. Header DTO Modification (Update to ADR 004)
Because a unique salt must be stored for the KDF, the binary DTO format grows from 41 bytes to **57 bytes**.

**New frame layout (57 bytes):**
| Field | Size (bytes) | Purpose |
| :--- | :--- | :--- |
| `MAGIC`  | 4  | Signature `SGB1` |
| `FLAGS`  | 1  | Bit mask (compression, plausible deniability) |
| `SALT`   | 16 | Salt for PBKDF2 (NEW) |
| `NONCE`  | 12 | AES-GCM initialization vector |
| `LENGTH` | 8  | Size of the original array (int64) |
| `MAC`    | 16 | Authentication tag |
| `DATA`   | N  | Ciphertext |

## 4. Encapsulation Pipeline (Embed Crypto Logic)
1. Generate random `SALT` (16) and `NONCE` (12).
2. Compute `AES_KEY = PBKDF2(Password, SALT, iterations=480000)`.
3. Encrypt the data (`Ciphertext, MAC = AES_GCM_Encrypt(AES_KEY, NONCE, Data)`).
4. Assemble the 57-byte header + `Ciphertext`.
5. Pass the assembled byte array to `SmartSpreader` and `LsbProcessor`.
